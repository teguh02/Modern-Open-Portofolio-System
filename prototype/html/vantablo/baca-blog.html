Memahami React Server Components Tanpa Drama

Server Components bukan sihir, dan bukan pengganti semua hal. Saya coba jelaskan dengan analogi dapur restoran supaya batas antara server dan client jadi lebih masuk akal.

TR

Teguh Rijanandi

Fullstack Developer

Setiap kali saya membuka diskusi soal React Server Components (RSC), polanya hampir selalu sama: ada yang sangat antusias, ada yang merasa ini overkill, dan ada yang bertanya, "jadi useEffect saya masih dipakai nggak?"

Jawaban singkatnya: masih, tapi tidak di tempat yang sama. Masalahnya, kebanyakan penjelasan soal RSC langsung masuk ke detail implementasi sebelum kita punya gambaran mental yang benar. Jadi mari kita mulai dari analogi yang lebih membumi.

Analogi: dapur dan meja makan

Bayangkan sebuah restoran. Ada dua area: dapur di belakang dan meja makan di depan.

Di dapur, koki bisa melakukan apa saja: memotong bahan, menyalakan kompor, mengambil stok dari gudang, bahkan membaca resep rahasia. Pelanggan tidak pernah melihat proses ini — yang mereka terima hanyalah makanan yang sudah matang dan tertata.

Di meja makan, tamu bisa melakukan hal-hal yang koki tidak bisa lakukan dari jauh: menambahkan garam sesuai selera, meminta sambal tambahan, memanggil pelayan, atau mengubah pesanan di tengah jalan.

Server Component itu koki. Client Component itu tamu. Perbedaan utamanya bukan soal "mana yang lebih baik", tapi soal siapa yang punya akses ke apa.

Intinya

Server Component berjalan di server, punya akses langsung ke database dan secrets, dan tidak mengirim JavaScript ke browser. Client Component berjalan di browser, punya state, event handler, dan bisa bereaksi terhadap interaksi pengguna.

Contoh nyata: kapan pakai yang mana

Ambil kasus halaman daftar produk. Yang perlu dilakukan halaman ini:

  • Mengambil daftar produk dari database.
  • Menampilkan nama, harga, dan stok.
  • Menyediakan tombol "Tambah ke keranjang" yang bisa diklik.

Bagian pertama dan kedua jelas milik koki. Kenapa harus mengirim query database ke browser kalau browser tidak butuh tahu bagaimana datanya diambil? 

// app/products/page.tsx
// Ini Server Component — tidak ada "use client" di sini
import { db } from '@/lib/db';
import AddToCartButton from './AddToCartButton';

export default async function ProductsPage() {
  const products = await db.product.findMany({
    where: { published: true },
    orderBy: { createdAt: 'desc' },
  });

  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>
          <span>{p.name}</span>
          <span>Rp {p.price.toLocaleString('id-ID')}</span>
          {/* Client Component di dalam Server Component */}
          <AddToCartButton productId={p.id} />
        </li>
      ))}
    </ul>
  );
}

Perhatikan bahwa db.product.findMany() dipanggil langsung di dalam komponen. Tidak ada API route, tidak ada fetch('/api/products'), tidak ada loading spinner. Komponen ini berjalan di server, jadi ia memang bisa bicara langsung ke database.

Sekarang bagian tamunya

Tombol "Tambah ke keranjang" butuh sesuatu yang koki tidak punya: reaksi terhadap klik. Itulah tanda paling jelas bahwa sebuah komponen harus jadi Client Component. 

// app/products/AddToCartButton.tsx
'use client'; // <-- ini yang menandai Client Component

import { useState } from 'react';

export default function AddToCartButton({ productId }: { productId: string }) {
  const [loading, setLoading] = useState(false);

  async function handleClick() {
    setLoading(true);
    await fetch('/api/cart', {
      method: 'POST',
      body: JSON.stringify({ productId }),
    });
    setLoading(false);
  }

  return (
    <button onClick={handleClick} disabled={loading}>
      {loading ? 'Menambahkan...' : 'Tambah ke keranjang'}
    </button>
  );
}

Hanya komponen ini yang dikirim sebagai JavaScript ke browser. Sisanya — termasuk seluruh proses query database — tetap tinggal di server.

Kesalahpahaman yang paling sering muncul

1. "Berarti semua komponen harus Server Component dong?"

Tidak. Aturan praktisnya sederhana: mulai dari server, turunkan ke client hanya saat butuh. Kalau sebuah komponen tidak punya state, event handler, atau API browser, biarkan ia tetap di server.

2. "Ini kan cuma SSR dengan nama baru."

Bukan. SSR mengirim HTML yang sudah dirender, tapi seluruh kode komponennya tetap dikirim ke browser untuk proses hydration. RSC benar-benar tidak mengirim kode komponennya sama sekali. Perbedaan ini terasa jelas di ukuran bundle.

3. "Jadi saya tidak butuh useEffect lagi?"

Untuk mengambil data — sering kali tidak. Tapi untuk hal seperti sinkronisasi dengan localStorage, WebSocket, atau library pihak ketiga yang tidak ramah SSR, useEffect masih tempatnya.

Kode terbaik adalah kode yang tidak perlu dikirim ke browser. Server Component memberi kita cara untuk memilih itu secara sadar, bukan sebagai efek samping.

Cara mulai tanpa menulis ulang semuanya

Saran saya: jangan migrasi seluruh aplikasi sekaligus. Mulai dari satu halaman yang datanya paling banyak diambil dari API. Pindahkan pengambilan datanya ke Server Component, lalu biarkan komponen interaktif di bawahnya tetap jadi Client Component.

  1. Pilih satu halaman dengan banyak fetch berantai.
  2. Pindahkan pengambilan data ke level halaman, di komponen server.
  3. Tambahkan 'use client' hanya pada komponen yang benar-benar butuh interaksi.
  4. Bandingkan ukuran bundle dan jumlah request sebelum-sesudah.

Setelah satu halaman berhasil, sisanya akan terasa jauh lebih jelas. Dan yang paling penting: Anda tidak perlu percaya pada hype — Anda bisa melihat sendiri angkanya di DevTools.
